## .dockerignore 的作用

`.dockerignore` 是一個文本檔案，位於 Dockerfile 同一目錄下，用來指定在構建 Docker 鏡像時應該忽略哪些檔案或目錄。它的作用類似於 `.gitignore`，可以幫助你減少構建上下文的大小，提高構建效率。

## Build Context是什麼
當你執行`docker build -t my-app`的時候，Docker做了什麼？

很多人會認為docker會讀取當前目錄中的Dockerfile，然後開始構建。

實際上執行這條命令的時候，Docker CLI會先把 . 目錄（也就是當前目錄）打包成一個tar檔案，這個tar檔案就是所謂的Build Context。

這個tar檔案會被傳送到Docker Daemon，然後Docker Daemon才會開始讀取Dockerfile並構建鏡像。

```bash
$ docker build -t my-app .
=> [internal] load build context
=> => transferring context: 1.37GB   # 👈 這裡
```

這意味著什麼？

即使你的 Dockerfile 只複製了幾個源碼文件，Docker 也已經把整個目錄傳輸過去了。你目錄裡的 node_modules、.git 歷史記錄、測試數據集，全部都打包在內——不管你用不用得到。
用一個具體的例子感受一下差距：

一個典型的 Node.js 項目，沒有 .dockerignore
``` bash
$ du -sh .
1.4GB    .

$ du -sh node_modules
1.1GB    node_modules

$ docker build -t my-app .
=> transferring context: 1.37GB   # 傳了將近 1.4GB
=> ...（等了 40 秒）
```

加上 .dockerignore 之後：
```bash
bash$ docker build -t my-app .
=> transferring context: 2.1MB    # 只傳了 2MB
=> ...（幾乎瞬間）
```

## 安全隱患

常見的Dockerfile寫法

```Dockerfile
COPY . .
```

簡單、方便，幾乎每個教程都這樣寫。但如果沒有 .dockerignore，這行指令會把你當前目錄下的所有東西都複製進鏡像，包括你完全沒有意識到的文件：
```
.env              # 數據庫連接字符串、第三方 API Key
.env.local        # 本地開發用的敏感配置
.git/             # 完整的 git 提交歷史
*.pem             # SSL 憑證私鑰
id_rsa            # SSH 私鑰
terraform.tfstate # 雲端基礎設施的完整狀態
```

Docker鏡像中的layer是永久的

一旦這些敏感文件被複製進鏡像，就算你後來修改了Dockerfile或刪除了這些文件，它們依然存在於鏡像的歷史層中，任何人都可以通過查看鏡像歷史來獲取這些敏感信息。

```bash
# 解包鏡像，直接翻出歷史 layer
$ docker save my-app | tar -xO --wildcards '*/layer.tar' | tar -t | grep .env
.env              # 就在這裡
```

## 和 .gitignore 的區別

`.dockerignore` 和 `.gitignore` 都是用來忽略文件的，但它們的作用對象不同：

差異一：只有一個文件，沒有繼承

.gitignore 可以在任意子目錄放置，形成層疊規則：

```text
project/
├── .gitignore          # 全局規則
├── src/
│   └── .gitignore      # 只影響 src/ 下的規則
└── docs/
    └── .gitignore      # 只影響 docs/ 下的規則
```

.dockerignore 只能放在項目根目錄，只有這一個文件，沒有子目錄繼承。所有規則都要寫在同一個地方。

差異二：最後匹配的規則優先

.gitignore 的規則是「從上到下，先匹配先生效」。

.dockerignore 剛好相反，最後一條匹配的規則優先。這在使用 !（排除）語法時特別容易出錯：

.dockerignore

目標：忽略所有 .env 文件，但保留 .env.example
```
.env*

!.env.example    # ✅ 這樣寫是對的，最後匹配到 .env.example 的規則是「不忽略」
```
但如果順序寫反了：

```
.dockerignore

!.env.example    # 先寫這行

.env*            # 後寫這行 —— 最終匹配 .env.example 的是這條，它會被忽略！
```

同樣的兩行，順序不同，結果完全相反。.gitignore 也有類似規則，但很多人沒有意識到 .dockerignore 的優先級邏輯需要特別留意。

差異三：Dockerfile 本身不會被排除

有些人會在 .dockerignore 裡寫：
```
Dockerfile
.dockerignore
```
本意是不想讓這兩個文件出現在鏡像裡。但其實 Docker daemon 會強制保留這兩個文件，寫了也沒有效果。

如果你真的不想讓 Dockerfile 出現在最終鏡像裡，應該在 Dockerfile 裡明確不 COPY 它，而不是依賴 .dockerignore。

## 模板

```text
# ===========================
# Version Control
# ===========================
.git
.gitignore
.gitattributes

# ===========================
# Secrets & Environment
# ===========================
.env
.env.*
!.env.example     # 保留示例文件，它不含真實密鑰
*.pem
*.key
*.p12
*.pfx
id_rsa*
*.cert

# ===========================
# Docker itself
# ===========================
Dockerfile*
docker-compose*
.dockerignore

# ===========================
# IDE & OS
# ===========================
.DS_Store
.idea/
.vscode/
Thumbs.db
*.swp
```

Node.js 追加
```text
node_modules/
npm-debug.log*
yarn-error.log*
.npm
dist/
build/
coverage/
.nyc_output/
```

python 追加
```text
__pycache__/
*.pyc
*.pyo
.venv/
venv/
env/
*.egg-info/
dist/
build/
.pytest_cache/
.mypy_cache/
htmlcov/
```

go 追加
```text
vendor/       # 如果在容器內執行 go mod download
*.test
*.out
```


結尾：三句話總結

- Build context 不是「Dockerfile 用到的文件」，而是「整個目錄」，大小直接影響 build 速度
- COPY . . 加上沒有 .dockerignore 是最常見的安全隱患，敏感文件一旦進入 layer 就無法真正刪除
- .dockerignore 和 .gitignore 互相獨立，有一個不代表有另一個，需要單獨維護
